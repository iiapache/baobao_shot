## 决策 D1：账号体系与家庭共享模式

- **背景**：APP 是否需要支持多宝宝档案 + 多家庭成员共同查看，决定后端复杂度与核心交互。
- **候选**：
  1. 单设备本地账号，1 个宝宝，无共享
  2. 单账号多宝宝，无共享
  3. 多账号绑定同宝宝，角色权限
  4. 完整家庭模式：多宝宝 + 多家庭成员 + 角色权限
- **决策**：采用 **#4 完整家庭模式**
- **理由**：
  - 隔代家人（爷爷奶奶）对「围观宝宝」的需求强，且常以「不愿打字、只想看」的角色出现
  - 双胞胎 / 多胎家庭在中国持续增长，单宝宝模型无法覆盖
  - 后期任何商业化（家庭礼包、影集打印）都需要家庭组实体
- **影响**：
  - 必须自建账号 / 家庭服务后端
  - 引入「管理员 / 家人 / 访客」三级权限
  - 邀请、转让、退出等流程纳入 V1.0 范围

## 决策 D2：照片与数据存储策略

- **背景**：宝宝照片是高敏感个人信息，需平衡隐私、家庭共享、成本三者。
- **候选**：
  1. 纯本地存储（无云）
  2. iCloud 同步
  3. 本地优先 + 用户自配置云盘
  4. 服务端云优先
- **决策**：采用 **#3 本地优先 + 用户自配置云盘（iCloud / 百度网盘等）**
- **理由**：
  - 妈妈用户群对「人脸入云被用于训练」高度警惕，本地优先是核心信任锚点
  - 通过让用户复用自有云盘空间，避免我方承担巨额存储成本
  - 仍可通过「发布机制」实现家庭共享，不牺牲核心使用场景
- **影响**：
  - 端侧需要内置 iCloud / 百度网盘 / 阿里云盘 等多个 OAuth + 文件协议适配器
  - 服务端不承载原图，仅承载已发布作品
  - 因家庭成员云盘账号各异，家庭共享必须走「已发布作品」中转

## 决策 D3：家庭共享与云盘的结合方式

- **背景**：用户既要家庭共享，又选了「本地 + 自有云盘」存储；两者在原图分发上存在天然冲突。
- **候选**：
  1. 服务端存缩略图 + 元数据，原图仅同步个人云盘
  2. 服务端临时存原图 30 天 + 个人云盘做长期备份
  3. 仅 iCloud 家庭共享相册
  4. 不同步到服务端，家人仅看「已发布」作品
- **决策**：采用 **#4 不同步到服务端，家人仅看「已发布」作品**
- **理由**：
  - 与 D2 的「本地优先」哲学一致，原图终身不上服务端，最大化隐私优势
  - 减少服务端存储成本与合规风险
  - 已发布作品本身就是「希望被看到的内容」，符合家人共享场景
- **影响**：
  - 「发布」成为家庭共享的唯一入口，UI 上需要弱化「私密相册 vs 发布相册」的认知摩擦
  - 家人圈看到的是策展过的精选，不是流水账，反而提升整体浏览体验
  - 取消发布等于服务端删除（保留本地副本）

## 决策 D4：MVP 范围

- **背景**：AI 与视频生成是产品差异化亮点，但接入成本和合规周期高，要决定首版是否一次性交付。
- **候选**：
  1. 极简 MVP（仅本地编辑 + 系统分享）
  2. MVP + AI 图片
  3. MVP + AI 图片 + AI 视频
  4. 完整版（全部 + 多模型 + 后端 + 家庭权限 + 发布对接）
- **决策**：采用 **#4 一次性完整交付**
- **理由**：
  - AI 是核心差异化，缺失 AI 的 MVP 在差异化上无法立项
  - 家庭权限与发布机制和账号体系深度耦合，分期反而引入双倍重构成本
- **影响**：
  - V1.0 工期约 4 个月，需并行启动算法备案（≥ 60 天）
  - 需要在 V1.0 内完成约 18 个 AI 玩法的产品包装与测试
  - 后端必须 V1.0 落地，含账号、家庭、发布、AI 调度、积分、订阅、广告

## 决策 D5：社交平台发布的接入深度

- **背景**：微信 / 小红书 / 抖音 三个国内主流社交平台，对第三方代发能力支持差异巨大。
- **候选**：
  1. 仅 iOS 系统分享面板
  2. 系统分享 + 智能贴文案
  3. 微信 OpenSDK 深度对接 + 其他系统分享 + 智能贴文案
  4. 优先做 APP 内家人动态圈，社交平台只走系统分享
- **决策**：采用 **#3 微信 OpenSDK 深度对接 + 其他平台走系统分享 + 智能贴文案**
- **理由**：
  - 微信是中国流量主入口，OpenSDK 仍是最佳官方通道，深度对接体验显著优于系统分享
  - 小红书 / 抖音 / 视频号 没有对个人号代发的官方开放能力，强行接入无可行性
  - 智能贴文案能补偿其他平台「系统分享」体验的不足
- **影响**：
  - PRD 明确写「微信仅支持朋友圈 / 好友，不支持公众号 / 视频号代发」
  - 需在小米/华为/Vivo 等渠道版本预留替换分享 SDK 的能力

## 决策 D6：照片输入方式

- **背景**：是否允许从系统相册导入照片，决定「时间锚定」准确度与补录灵活度。
- **候选**：
  1. 仅 APP 内拍摄
  2. 拍摄 + 导入（以 EXIF 拍摄时间为准）
  3. 拍摄 + 导入 + 允许手动改时间
- **决策**：采用 **#2 拍摄 + 导入，以 EXIF 拍摄时间为准**
- **理由**：
  - 现实中爸爸 / 隔代家人常用系统相机拍照，必须支持补录
  - 强制使用 EXIF 拍摄时间，保证「成长天数」与真实日期不被人为操纵
  - 防止「漏拍补录」时被用户当成「PS 一天的拍照打卡」滥用
- **影响**：
  - 导入流程必须解析 EXIF；缺失 EXIF 弹窗禁止导入
  - 当 EXIF 早于出生日时，引导孕期模式（V1.1 待定）

## 决策 D7：成长时间体系与里程碑

- **背景**：是否包含孕期、里程碑提醒的覆盖面，影响产品文化定位（中式 vs 国际化）。
- **候选**：
  1. 仅出生后简单天数
  2. 出生后 + 中国传统里程碑（三朝、满月、百天、周岁等）
  3. 含孕期模式 + 出生后里程碑
  4. 孕期模式独立可选
- **决策**：采用 **#2 出生后 + 中国传统里程碑**
- **理由**：
  - 中国家庭对三朝、满月、百天、抓周等仪式感强，是关键产品差异化
  - V1.0 暂不背孕期模式以收敛工期，孕期模式放入 V1.1 候选
- **影响**：
  - V1.0 内置 10+ 个里程碑模板，每个都有推送 + 模板 + 推荐 AI 玩法
  - 海外英文版未来需要替换为西方育儿里程碑（三个月翻身、六个月辅食等）

## 决策 D8：AI 后端架构与合规策略

- **背景**：国内合规要求所有生成式 AI 必须备案，海外模型未备案不可在中国区上架；同时海外用户希望使用 GPT / Gemini 等头部模型。
- **候选**：
  1. 自建后端 + 仅国内模型，只在中国上架
  2. 自建后端 + 双区域调度，海外用 OpenAI / Google
  3. 仅海外上架，仅接入海外模型
  4. 中国先上 + 海外延后
- **决策**：采用 **#2 自建后端代理 + 双区域调度**
- **理由**：
  - 不放弃任一市场；中国走备案模型，海外走头部模型
  - 自建代理层可解耦模型升级与端侧版本发布，便于动态切换与对账成本
- **影响**：
  - 后端按用户区域（基于注册地 / 当前网络）路由
  - 海外区涉及个人信息出境，需补签出境标准合同或仅对成年用户开放
  - 端侧只暴露「玩法」，不暴露「模型名」，避免用户混淆

## 决策 D9：商业化模型

- **背景**：积分 / 订阅 / 广告三种模式的组合方式决定商业化天花板与用户体验。
- **候选**：
  1. 纯积分制
  2. 订阅 + 积分双轨
  3. 免费看广告 + 积分
  4. 积分 + 广告激励
- **决策**：采用 **#3 免费看广告 + 积分**，并补充 **订阅去广告**
- **理由**：
  - 中国家庭用户对订阅敏感，但对「看广告免费用」接受度高
  - AI 算力成本浮动大，订阅包含 AI 易导致成本失控；积分按量结算最公允
  - 订阅作为「去广告 + 增值」入口（关品牌水印、年度回顾重生成等），不与 AI 算力绑定
- **影响**：
  - 接入开屏 / 插页 / 激励三类广告位
  - 充值走 Apple IAP（30% 抽成需在定价时计入）
  - 看激励广告获积分作为低门槛免费获取通道
